# Kitrack 購入候補の使用色 設計

## 目的

Kitrackの買い物リストに保存した購入候補にも、所有キットと同じ操作で使用色を登録できるようにする。使用色一覧、追加元の選択、詳細、編集、削除、ドラッグ並び替えを共通化し、Boxへ移動したときは使用色を新しい所有キットへ引き継ぐ。

本設計は購入候補と所有キットを完全に分離する既存方針を維持する。購入候補の使用色と所有キットの使用色は同じレコードを共有せず、移動後も同期しない。

## 用語とライフサイクル

- **購入候補**: 購入を検討しているキット。Boxと制作ステータスを持たない。
- **所有キット**: 所有している物理キット1個。Box、制作ステータス、写真、使用色を持つ。
- **キット使用色**: 購入候補または所有キットのどちらか一方に属する色の計画。保存済み混色とは独立する。
- **Boxへ移動**: 購入候補を削除し、選択したBoxへ新しい所有キットを作る所有状態への変換。

Boxへ移動すると、候補の使用色の名前、メモ、構成塗料、配合率、塗料順、色順を新しい所有キットへコピーする。コピー完了後に候補側を削除し、両者を結ぶIDや同期状態は残さない。

## 採用する構成

### 独立した候補用テーブル

所有キット用の `kit_colors` / `kit_color_paints` は変更せず、購入候補専用の子テーブルを追加する。

```sql
CREATE TABLE IF NOT EXISTS kit_wishlist_colors (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  wishlist_id INTEGER NOT NULL,
  name TEXT,
  note TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  added_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS kit_wishlist_color_paints (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  wishlist_color_id INTEGER NOT NULL,
  paint_id INTEGER NOT NULL,
  ratio REAL NOT NULL,
  sort_order INTEGER NOT NULL DEFAULT 0
);
```

既存の購入候補には使用色を推測して追加せず、空の状態から開始する。

### UIと操作の共通化

所有キットと購入候補で、次の表示と操作を担う使用色パネルを共通化する。

- 使用色カード一覧
- ドラッグ＆ドロップ並び替え
- 「使用色を追加」と追加元3択
- 塗料から選ぶ
- 保存済み混色からコピーする
- 新しく混色を作る
- 色詳細、色情報の編集、削除
- 読み込み、空状態、保存中、失敗時の表示

共通パネルは保存先テーブルを直接判断せず、親画面から渡された一覧と追加・更新・削除・並び替え処理を呼ぶ。所有キット用と購入候補用のDB処理は独立させる。

所有キットと購入候補の入力項目、Box、制作ステータス、購入操作まで一つの巨大な共通モーダルにはしない。共通化する範囲は使用色の体験に限定する。

## 購入候補の画面

### 新規登録

新しい購入候補は、現在と同じ追加フォームで名前、メーカーなどを保存する。まだ購入候補IDがない登録途中では使用色を入力しない。

使用色は一度買い物リストへ保存した後、一覧の行を開いて登録する。この流れは、所有キットを追加してからキット詳細で使用色を登録する現在の挙動と揃える。

### 保存済み購入候補の詳細

買い物リストの行をタップすると、所有キット詳細と同じ情報構造を持つ購入候補詳細を開く。

- 上部にキット名、メーカー、スケール、写真を表示する。
- 「詳細情報」と「使用色」の2タブを表示する。
- 詳細情報では名前、メーカー、シリーズ、種別、スケール、価格、メモ、写真を編集できる。
- 使用色では共通パネルを表示する。
- Boxと制作ステータスは表示しない。
- Boxへ移動と削除は購入候補の操作として引き続き提供する。

詳細情報の編集モードへ入ると「詳細情報」へ移動して使用色タブを隠す。詳細情報の編集を保存または終了した後に使用色へ移れるようにし、未保存の詳細項目と使用色の即時保存を同時に操作させない。

現在の購入候補編集用 `AddKitModal` は新規登録に残し、既存候補の閲覧・編集は購入候補詳細へ移す。これにより、詳細項目の未保存変更と、即時保存される使用色操作が同じ保存ボタンへ混在することを避ける。

## 使用色の操作

購入候補でも所有キットと同じ3つの追加経路を提供する。

1. **塗料から選ぶ**: 1色・100%の使用色を作る。
2. **保存済み混色から選ぶ**: 名前、メモ、構成塗料、ratio、塗料順を独立レコードとしてコピーする。
3. **新しく混色を作る**: 1〜5色、同一塗料種別、整数パーセント、合計100%の既存検証を使う。

購入候補の使用色を編集・削除しても、保存済み混色と所有キットには影響しない。Box移動後に所有キット側の使用色を編集しても、Undo用スナップショット以外に候補との同期は行わない。

並び替えは共通カード右端のドラッグハンドルを使い、保存失敗時は画面上の順番を元に戻してエラーを表示する。スクリーンリーダー向けに「上へ」「下へ」の代替操作を維持する。

## DB操作と整合性

購入候補用に、所有キットの使用色操作と同じ契約を持つDB関数を用意する。

- 一覧取得
- 1色／混色の追加
- 名前、メモ、構成塗料の更新
- 削除
- 並び替え

親色と構成塗料の追加・更新・削除は一つのトランザクションで行う。候補本体の削除、買い物リスト初期化、Box移動、Undoでも、候補使用色の子行を同じ整合単位に含める。

購入候補が存在しないIDへの追加・更新、または別候補の色IDを渡した操作は失敗させる。画面を閉じた後の遅い読み込み結果や連打による二重保存を反映しない。

## Boxへの移動とUndo

購入候補からBoxへの移動は、次を一つの排他トランザクションで行う。

1. 選択したBoxへ所有キットを作成する。
2. 候補写真を所有キット写真へコピーする。
3. 候補使用色を所有キット使用色へコピーし、新旧の色IDを対応付ける。
4. 各候補色の構成塗料を対応する所有キット色へコピーする。
5. 候補使用色の構成塗料、候補使用色、候補写真、購入候補本体を削除する。

途中で失敗した場合は全変更をロールバックし、購入候補を残す。

移動結果のUndo用スナップショットには、購入候補本体、写真、使用色、構成塗料を含める。Undoは作成した所有キットとその写真・使用色を削除し、候補本体と全子データを復元する。作成した所有キットIDで対象を特定し、同名キットには触れない。

## 削除、初期化、塗料参照

- 購入候補削除時は本体、写真、使用色、構成塗料をまとめてUndo用スナップショットへ保存する。
- Undoしなかった場合も、使用色はDBデータだけなので追加の物理ファイル掃除は不要とする。
- 「キット買い物リストを初期化」は候補色の構成塗料、候補色、候補写真、候補本体の順で削除する。
- 「キット保管箱を初期化」は候補使用色を削除しない。
- 手動登録塗料の削除・カタログ初期化・シード更新では、候補使用色から参照中の塗料も使用中として保護する。

## クラウドバックアップ

バックアップスキーマをv7へ更新し、購入候補使用色を追加する。

- `kitWishlistColors`: 候補localRef、色localRef、名前、メモ、sort_order、added_at
- `kitWishlistColorPaints`: 色localRef、catalog_code、ratio、sort_order

バックアップ作成時は候補本体、候補色、構成塗料を同じDBスナップショットから読む。復元時は候補localRefと色localRefを新しいローカルIDへ対応付け、親が存在する行だけを復元する。

v1〜v6バックアップには候補使用色がないため、候補本体と写真を従来どおり復元し、候補使用色は空にする。新しいバックアップを古いアプリで復元させない既存のバージョン上限制御を維持する。

候補使用色は写真バックアップ権限とは無関係な通常データとして、クラウドバックアップ対象に含める。

## エラー処理

- 使用色の読み込み失敗時は詳細画面を閉じず、使用色タブ内に再試行を表示する。
- 追加・編集・削除・並び替えの失敗時は、入力または直前の表示順を保持する。
- Box移動、削除、Undoの失敗時は本体・写真・使用色の一部だけを残さない。
- 保存中は同じ対象への操作を無効化し、二重登録や二重移動を防ぐ。
- 使用色詳細や追加元選択を開いている間は、親モーダルの戻る・閉じる操作と競合させない。

## 検証

- 新規購入候補では使用色入力を求めず、保存後の詳細から使用色を追加できる。
- 候補詳細にBoxと制作ステータスが表示されない。
- 3つの追加経路、詳細、編集、削除、並び替えが所有キットと同じ挙動になる。
- 候補と所有キットのどちらで編集しても、他方や保存済み混色へ同期しない。
- Box移動で全写真、全使用色、構成塗料、ratio、各順序が所有キットへ引き継がれる。
- 移動失敗時に候補の本体、写真、使用色がすべて残る。
- Undoで所有キット側が削除され、候補の本体、写真、使用色が復元される。
- 候補削除のUndoでも写真と使用色が復元される。
- 買い物リスト初期化とキット保管箱初期化が互いのデータを削除しない。
- 候補使用色で参照中の手動塗料を削除できない。
- v7バックアップの往復で候補使用色が復元される。
- v1〜v6バックアップを復元すると候補使用色が空のまま正常終了する。
- `npm run test`、`npm run typecheck`、`git diff --check` が成功する。
- Expo Go実機でモーダル遷移、戻る操作、ドラッグ、長い色名、VoiceOverを確認する。

## 対象外

- 購入候補のBoxまたは制作ステータス。
- 購入候補と所有キットの永続リンクや編集同期。
- 同じ候補から複数の所有キットを作る機能。
- 使用色の数量、価格、在庫引当。
- 候補使用色と保存済み混色の自動同期。
- 新規購入候補の保存前に使用色を入力する機能。
- 新しい状態管理、モーダル、ドラッグ＆ドロップの外部ライブラリ。
